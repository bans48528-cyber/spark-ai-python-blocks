# Development Guide

This guide explains how the converter is organized and how to extend it safely.

## Repository Layout

```text
tools/
  sparkai_reverse.py        Python -> Spark AI block graph and .sparkai archive
  sparkai_clipboard.py      Spark AI block graph -> pasteable Blockly XML
  sparkai_ai.py             DeepSeek-compatible AI API generation and validation
  sparkai_web.py            local AI chat and paste-and-generate web UI
  sparkai_tool.py           inspect/validate/compare/generate CLI
  test_*.py                 regression tests

templates/
  base.sparkai              fixed empty-project template used for .sparkai output

examples/
  *.py                      user-facing examples and regression inputs

docs/ai_rules/
  ai_generation_rules.md    compact rules injected into AI generation requests
  hardware_overview.md      compact hardware model and default port conventions
  supported_functions.md    compact function list for AI generation
  prompt_templates.md       backend prompt assembly examples
```

The ignored `work/`, `generated/` and `outputs/` directories are local scratch
areas. They should not be required by a clean clone.

## Core Data Flow

```text
Spark AI Python source
  -> ast.parse
  -> SparkAIReverseCompiler.prepare_variables()
  -> SparkAIReverseCompiler.prepare_customs()
  -> statement/expression compilation
  -> Scratch 3 style block dictionary
  -> validate_generated_inputs()
  -> .sparkai archive or clipboard XML
```

The `.sparkai` output is a ZIP file. The compiler reads
`templates/base.sparkai`, replaces the sprite block graph, writes stage
variables/lists and preserves the template assets.

Clipboard XML is generated from the same block dictionary. It does not include
the start-hat block, because Spark AI's workspace paste operation expects a
stack that can be placed under the existing start block. Custom block
definitions are emitted as separate XML fragments before the main stack.

## Important Design Rules

- Only generate blocks that exist in the Spark AI UI.
- Reject unsupported functions with `ReverseCodeError`.
- Reject generated input shapes that cannot be produced by the real UI.
- Keep mappings explicit when Python cannot contain enough visible workspace
  information, especially custom block labels.
- Add or update tests before declaring a new block supported.

## Adding Support for a New Function

1. Create a small program in Spark AI using the target block.
2. Copy the Python generated by Spark AI.
3. Save a minimal example in `examples/` if it is useful to users.
4. Inspect the `.sparkai` project or copied Blockly XML to find:
   - opcode
   - fields
   - inputs
   - shadow block types
   - dropdown values
5. Add a branch in `SparkAIReverseCompiler.statement()` or
   `SparkAIReverseCompiler.expression()`.
6. Add validation in `validate_generated_inputs()` if the block has special UI
   slots such as motor dropdowns, sensor ports, sliders or fixed numeric inputs.
7. Add a regression test in `tools/test_sparkai_reverse.py` or
   `tools/test_sparkai_clipboard.py`.
8. Run:

```powershell
python -m unittest discover -s tools -p "test_*.py"
```

## Variable And List Mapping

Mapping comments are parsed in `sparkai_reverse.py`.

Supported forms:

```python
# @sparkai-variable PythonName => DisplayName
# @sparkai-list PythonName => DisplayName
# @var PythonName=DisplayName
# @list PythonName=DisplayName
```

The compiler stores both Python names and display names in `VariableInfo` and
`ListInfo`. The `.sparkai` writer uses the display name in stage metadata and
block fields. Clipboard XML uses the display name in `<field>` text and remaps
field IDs to fresh `clipboard-variable-*` / `clipboard-list-*` values for each
generation.

## Custom Blocks

Custom block definitions use `CustomInfo` and `CustomArgumentInfo`.

The Python function body can be converted, but the visible custom-block
template cannot be recovered from Python alone. The template must be supplied:

```python
# @sparkai-custom functionName => visible label %n enabled %b
# @sparkai-custom-arg functionName PythonArg => VisibleArg
```

The generated block graph contains both the procedure definition and the call
blocks. Clipboard mode emits definitions first and the main program last.

## Testing Notes

The normal test command is:

```powershell
python -m unittest discover -s tools -p "test_*.py"
```

`tools/test_sparkai_tool.py` has one optional desktop-project test that is
skipped unless a local desktop sample exists. This keeps the public test suite
portable.

The tests should not depend on `work/`, `generated/` or `outputs/`.

## Web UI

Start the web UI:

```powershell
.\Start-SparkAI-Generator.cmd
```

The double-click launcher resolves paths relative to its own location, checks
for Python 3.10+, starts the local server and opens the browser.

Direct server start:

```powershell
python tools\sparkai_web.py --host 127.0.0.1 --port 8765
```

The web UI is deliberately small and uses only the Python standard library. It
posts chat requests to `/chat`, receives a validated Python candidate, then
posts code to `/generate` to either return clipboard XML fragments or write a
`.sparkai` file under `generated/`.

## AI Integration Notes

The converter remains deterministic and local. The AI layer is intentionally
separate from the converter:

```text
user chat
  -> backend injects docs/ai_rules/*.md
  -> AI returns JSON
  -> backend extracts the python field
  -> SparkAIReverseCompiler validates it
  -> backend repairs or shows the code candidate
  -> user chooses clipboard XML or .sparkai generation
```

For the first version, keep context assembly simple:

- include `ai_generation_rules.md` on every AI request
- include `hardware_overview.md` on every AI request
- include `supported_functions.md` on every code-generation or repair request
- include a compact project-state summary instead of unbounded raw chat history
- optionally include one short example when useful

Because the rule files are compact, this is simpler and safer than adding
keyword routing or vector retrieval too early.

The web endpoint is `/chat`. It accepts JSON with:

- `message`: latest user request
- `api_key`: optional temporary DeepSeek key supplied by the page
- `conversation_summary`: compact previous chat text from the page
- `current_python`: current candidate code, used only to summarize state

The API key is not written to disk. If `api_key` is empty, the server reads
`DEEPSEEK_API_KEY` from the private local `.env` file first, then from its
process environment. `.env` is ignored by Git; commit only `.env.example`.

The AI CLI smoke-test entry point is:

```powershell
$env:DEEPSEEK_API_KEY = "your-api-key"
python tools\sparkai_ai.py generate "生成一个巡线小车，左右电机接 E/F，左右灰度接 A/B"
```

Never commit real API keys. The key is read only from `DEEPSEEK_API_KEY`.

## Release Checklist

- Run the full test suite.
- Confirm `examples/line_follower.py` can generate both XML and `.sparkai`.
- Confirm `.gitignore` excludes generated artifacts.
- Check that no local paths or extracted Spark AI source files are required.
- Keep `templates/base.sparkai` in the repository unless the project switches
  to a user-supplied template workflow.
